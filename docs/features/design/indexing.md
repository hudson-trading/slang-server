# Workspace Indexing

slang-server's indexing system provides fast symbol lookup and navigation across large SystemVerilog codebases by building and maintaining an index of top level symbols.

The indexer uses multithreading to rapidly index your repo. Crawling a file system actually often takes longer than parsing in large unconfigured repos, so make sure your indexing config is as specific as possible.

In each syntax tree parsed, it indexes the top level symbols like moduldes, packages, etc, as well as references to other top level symbols. If no top level symbols were found, it'll instead index the macros defined in that file.

The index also tracks filenames, including headers that contain fragments of a class or package. Matching uses the entire relative include path: `detail/types.svh` matches a file ending in `detail/types.svh`.

Available include filenames are a snapshot of the last full indexing pass. A separate index maps the filenames in gathered include strings to their containing files, without resolving those strings or checking their targets on disk. Gathered references, symbols, macros, and header declarations track file changes.

When a header needs a compilation context, only references with its filename are resolved, using local paths before the nearest indexed matches. Results are cached until index or parsed-buffer updates. Actual parsed relationships override gathered references, including when parsing confirms that a source has no active includes. Macro-only headers skip this resolution.

The logs report parsing and metadata indexing, include filename indexing, and their total separately; directory discovery has its own timing.

For shallow editor analysis, the server derives additional include directories from the nearest indexed matches for unresolved quoted includes. These paths belong only to that syntax tree's options; the shared source manager and configuration are unchanged. Distance is measured from the file containing each include, and nested headers can contribute additional paths. Equally close matches are resolved in canonical path order; filesystem aliases of the same file count as one match. Existing configured and file-local resolutions take precedence. Because a syntax tree has one search order, inferred paths are skipped if they would select conflicting headers within that tree. Files supplied through build files and system includes (`<...>`) keep normal include lookup.

The **Add include** quick fix inserts an include for an unresolved macro or a declaration found in a header. Each matching header is offered separately, preferring a spelling that resolves through configured search paths or the current file's directory, then trying an explicit relative path. A unique filename alone does not justify shortening the include path. Macro includes follow the last include before the usage, preserving existing include order and leading file comments. Declaration includes precede the enclosing member in its package or module scope, keeping earlier imports and declarations available; references in a module header are handled before the module declaration. Existing includes are not duplicated.

Files with potential includers are eligible for include-context lookup regardless of extension. Files containing only macro definitions remain standalone and do not show include-context CodeLenses. Context discovery uses the filename index and parsed reverse include relationships without scanning the workspace. An opened file shares an enclosing source file's shallow compilation. When several contexts are available, the server defaults to the first active context in canonical source-path order; an explicit selection on an include list also guides its nested headers. For a package that includes a list of class files, opening either the list or a class file uses the package's imports, macros, and declaration order. Include relationships update with parsing and saves; file indexing invalidates outdated relationships and refreshes the gathered references.

`ShallowCompilation` owns the syntax trees, active-design context, elaboration, and cached diagnostics. Each open file has a `ShallowAnalysis` with its own buffer, token and symbol indexes, and outline; published diagnostics are filtered to that file. Editing an included file invalidates the shared compilation; files without an active enclosing context retain standalone analysis.

**Expand Macros** expands invocations in the selected file using the definitions active at each invocation, including definitions inherited from its includer. It preserves that file's comments, whitespace, and include directives.

Included files show an **Included by filename:line** CodeLens at the top of the file. Clicking it opens the include directive in the immediate parent file. When multiple contexts are available, a second **And N others** CodeLens opens a picker showing their include sites and enclosing sources. Selecting a context switches the file's shared compilation, updates diagnostics and editor annotations, and keeps the editor in place. The choice survives document edits and configuration reloads; if it is no longer available, analysis falls back to another active context. Repeated includes within one source can be selected separately. Include relationships use canonical filesystem paths, so directory aliases do not create duplicate contexts.
