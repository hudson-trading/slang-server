# Language Features

### Diagnostics

Diagnostics are provided by slang using [Shallow Compilations](design/shallow.md) when a design is not set.
When a [design is set](hdl/hdl.md), the shallow compilation provides diagnostics on each keystroke, and the design's compilation provides diagnostics on each save.

Saving a dependency also refreshes diagnostics in open files that depend on it, even without a design set. For example, saving a header that changes a port width updates width-mismatch diagnostics in an open parent module.

### Hovers and Go-to Definition

Hovers are provided on each symbol with the following info if applicable:

- Symbol kind, or Syntax kind in the case of macros.
- Lexical Scope, or file in the case of macros.
- Resolved type info
- Bitwidth, if a value or type
- Value, if a constant value
- The syntax that the symbol is derived from
- Macro usage, if symbol was defined from one.
- Port direction and resolved interface type parameters.
- Driver source snippets, including the macro invocation when a driver is generated by a macro.

Named types in hovers link to their declarations. When a type cannot be fully resolved, hovers show its declared form where available.

A token can refer to multiple symbols. Hovers and Go-to Definition include both sides of implicit port connections such as `.data`, the type and direction declarations of modport members, and relevant symbols in package imports and exports. Struct assignment field names also support hovers and Go-to Definition.

Built-in system tasks and functions such as `$bits` have hovers with signatures and documentation.

With an elaborated design, hovers use the [active instance](hdl/hdl.md#active-instances) of the enclosing module or interface. Parameter values, dependent types and widths, interface connections, and driver information therefore reflect the selected instance rather than the default elaboration.

### Completions

Completions are currently provided for most constructs:

- Generic expression completions: parameters, variables, types etc.
- Global symbols - Modules, Interfaces, Packages
- Functions and macros
- Built-in system tasks and functions, triggered by `$`
- Hierarchical references and struct members
- Struct assignment patterns

![goto-refs](/assets/images/completions.gif)

#### Struct assignment patterns

Typing `'{` in a context with a known struct type offers a snippet containing all its fields. Within a named pattern, completion suggests remaining field names and `default`.

```systemverilog
typedef struct packed {
    logic [7:0] payload;
    logic valid;
} packet_t;

module example;
    packet_t packet;
    initial packet = '{payload: '0, valid: 1'b1};
endmodule
```

In this example, typing `'{` after `packet =` offers `payload` and `valid` entries with editable values. Hovering either field name shows its declaration, and Go-to Definition opens the field in `packet_t`. Nested assignment patterns infer their field types from the enclosing pattern. [Assignment pattern type hints](#inlay-hints) show the inferred type inline.

#### Nested and incomplete types

After typing `value.`, completion includes nested struct paths such as `header.length`, so you can search for a deeply nested field without completing each level separately. Arrays and unions are not recursively flattened into these paths; navigate into them explicitly.

Known fields remain available when part of a struct type is unresolved, for example when a width depends on a missing parameter. Completions also handle interface port arrays and multidimensional instance arrays. Resolved interface type parameters supply member types when available.

### Go-to References / Rename

Go-to references are provided for nearly all symbols except for macros. References and rename connect both sides of implicit port connections. Keep in mind this is an expensive operation, and may take some time for a large repo.

### Inlay Hints

Inlay hints are text that show up inline in the code to provide useful info. They can be hovered for more info, and some can be double clicked to insert some text.

**Ports Types** - Show the type of ports in instances (off by default)

![goto-refs](/assets/images/port_inlays.png)

**Wildcard Ports** - Show which signals are passed through
![goto-refs](/assets/images/port_wildcard_inlays.png)

**Positional args in Macros, Functions, Parameter/Port lists** - Show the argument names
![goto-refs](/assets/images/macro_inlays.png)

**Active parameter values** - Show resolved parameter and localparam values for the [active instance](hdl/hdl.md#active-instances). These hints are enabled by default and can be controlled with `inlayHints.activeParameterValues`.

**Assignment pattern types** - Show the inferred struct or union type before an untyped `'{...}` pattern, including nested patterns. In the example above, the hint displays `packet_t` before `'{payload: ...}`. The hint links to the type declaration and can insert the explicit type in clients that support inlay-hint edits. Enabled by default; configure it with [`inlayHints.assignmentPatternTypes`](/start/config.md#inlayhints).

### Document Outline and Sticky Scroll

The document outline includes modules, interfaces, classes, declarations, instances, and procedural and generate scopes. Multiline constructs such as `always` blocks, conditionals, loops, and case statements have ranges covering their bodies, allowing editors to keep enclosing scopes visible while scrolling.

In VS Code, enable **Editor: Sticky Scroll Enabled** (`editor.stickyScroll.enabled`) to use these ranges. Other editors can use the standard document-symbol response for outlines and scope navigation.
